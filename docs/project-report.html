01 · At a glance

Executive summary

Red Flag Radar is a local-first web application that helps a person examine suspicious messages, a sequence of messages, or the visible text of a URL. It explains which wording or sequence triggered a rule, suggests independent checks, and offers a context-aware next move.

Its central promise: replace a bare “safe/scam” label with evidence, context, and a practical action. Its score is a heuristic signal, never a probability or proof.

Who it helps

Students reviewing internship and scholarship offers, people receiving unexpected payment or account messages, and anyone who wants to pause and check a link or conversation.

What it does

Flags a small set of explainable warning signs, preserves conversation order, displays a verification plan, and proposes an optional safe response.

What it avoids

It does not open submitted URLs, contact third-party AI services, authenticate a sender, or save analysis submissions in a database.

Project status

Three working services: React/Vite UI, Java Spring Boot API, and Python FastAPI detector. Tests and local browser flows have been run; this remains a prototype.

Product idea in one sentence

Help people slow down, understand why a message deserves scrutiny, and verify important claims through a source they find independently.

How to read this report

The first half explains the user need and the product experience. The middle describes the architecture, data contract, and rule engine. The final sections cover privacy, setup, quality checks, limitations, and a sensible roadmap.

02 · The problem

Why this project exists

Fraudulent messages can mix ordinary details with a sudden request: pay a fee, share an access code, act before a deadline, or follow a supplied link. A single sentence may be ambiguous. A conversation’s progression can be more revealing than one line considered alone.

Many basic tools return a label without explaining it. That can encourage overconfidence: a “low risk” result may be mistaken for a safety guarantee. Red Flag Radar instead shows the evidence and frames the score as one imperfect signal.

Design goals

  • Explainable: make each rule and its reason visible.
  • Context-aware: keep conversation order and identify selected sequences such as a fee after an offer.
  • Actionable: translate findings into independent verification steps and optional cautious wording.
  • Privacy-minded: analyze locally and avoid storing submitted text by default.
  • Careful: do not claim a sender, organization, or website has been verified.

03 · Product experience

What the user can do

1. Review one message

Paste an offer or message. The result shows the heuristic score, risk band, highlighted wording, evidence explanations, recommendations, and checks.

2. Review a conversation

Paste messages one per line. The detector keeps their order, shows a per-message timeline, and looks for selected patterns such as payment after selection or later time pressure.

3. Review URL text

Submit an absolute HTTP or HTTPS URL. The service examines its scheme and host text; it never requests the destination.

4. Verify independently

Use the interactive checklist as personal progress. Its completion is not transmitted as evidence and does not prove an offer is legitimate.

Distinctive feature — Next Move Coach

After an analysis, the coach uses the returned evidence codes to present a concise optional next step. Payment findings prompt a pause-and-verify response; credential findings discourage sharing passwords, one-time codes, and financial information; urgency findings give the person room to check the deadline. The user can copy the suggested text and edit it.

For URL reviews, the coach changes from a reply template to an action: do not open the link from the message; type a known organization address independently. It explicitly says that replying is optional and the suggestion cannot verify the sender.

User journey

  1. Choose message, conversation, or URL review.
  2. Enter text and submit it to the local Java API.
  3. See the score, plain-language summary, evidence, and (for a conversation) timeline and patterns.
  4. Read an optional next move, copy it if useful, and consult the verification checklist.
  5. Independently confirm important claims before paying, sharing data, or acting.

Interface states

Empty inputs keep the analyze control disabled. An unsupported URL scheme displays an inline validation message. During a request, the button is disabled and a loading status is shown. The result view includes a reset action, and checklist progress updates as the user checks items.

Non-technical value: the product is designed to reduce rushed decisions and show a user what to verify next, rather than ask them to trust an opaque automated verdict.

05 · Detection method

How the rule engine works

The current service is intentionally deterministic and rule-based. It does not call a hosted language model, use a trained classifier, browse the web, or check a reputation database. Matching and scoring are visible in source code and tests.

Message indicators

IndicatorIllustrative triggerWeight
Payment requestPay, payment, fee, deposit, wire, transfer, send money25
Sensitive informationCredential or financial term near a request to send/share/provide it35
UrgencyImmediately, today, right now, final notice, short deadline12
Pressure or threatCancellation, loss, legal action, termination threat12
Unusually attractive claimGuaranteed, easy money, no experience required10

Conversation patterns

  • Payment after offer: a payment-related message appears after a selection or offer claim; adds 15 points.
  • Increasing urgency: time pressure appears later after earlier messages without an urgency signal; adds 10 points.
  • Each message also receives its own evidence and risk band, so the timeline can show where signals occurred.

URL indicators

IndicatorWeight
HTTP rather than HTTPS15
User information embedded before the host25
Numeric IP address as host15
Punycode host label20
One of the selected uncommon suffixes (.zip, .mov, .top, .click, .work)8

These are URL-shape observations, not reputation or safety checks. A legitimate site can use an IP, HTTP, or an uncommon suffix; any signal can be wrong.

Score calculation

For repeated evidence with the same code, the engine keeps the highest weight rather than repeatedly adding it. Distinct codes are summed, then capped at 100.

score = min(100, sum(max weight for each distinct evidence code))
Low: score < 30    Medium: 30–59    High: score ≥ 60

The bands are presentation categories for a heuristic estimate; they are not calibrated probabilities. The detector also avoids counting common denial phrases such as “no fee” as a fee request in the covered pattern.

Analysis limits

Messages and URLs are limited to 10,000 characters. A conversation accepts at most 20 non-empty ordered entries. Optional timestamps are descriptive metadata (up to 80 characters), not a source of external validation.

06 · API and data

Contract, errors, and privacy

Public endpoints

ServiceRoutePurpose
JavaGET /api/healthAPI health response.
JavaPOST /api/analyzeBrowser-facing JSON analysis endpoint.
PythonGET /healthDetector health response.
PythonPOST /analyzeInternal detector endpoint called by Java.

Request modes

{ "mode": "single", "message": "..." }
{ "mode": "conversation", "messages": [{ "text": "...", "timestamp": null }] }
{ "mode": "url", "url": "https://example.org/path" }

Analysis response

The JSON response contains riskScore, riskLevel, summary, evidence, messageFindings, patterns, recommendations, and verificationChecklist. Evidence uses zero-based message indexes; conversation-wide patterns can have a null index.

Error behavior

  • Invalid request content returns HTTP 422 with a generic safe detail rather than echoing the submitted message or URL.
  • If Python is unreachable, Java maps the upstream failure to HTTP 503.
  • If the detector returns an invalid response shape, Java reports HTTP 502.
  • Browser-side validation gives immediate feedback for empty input, unsupported URL scheme, and size/message-count limits.

Privacy and trust boundaries

  • The normal analysis path is local browser → Java → Python. No external AI provider is configured.
  • The application has no database or persistence layer for analysis submissions. Checklist state is held in the browser UI.
  • The detector parses URL text only. It does not open or fetch a submitted address.
  • Submitted text should not be logged. It is untrusted input and must remain size-limited and validated at each service boundary.
  • Do not paste credentials, one-time codes, account numbers, or private information into a demo.
Important distinction: privacy-first local processing does not mean a message is safe. A low score does not establish legitimacy, and checking every box does not prove a sender or offer is genuine.
07 · Running and quality

Setup and verification

Prerequisites

  • Python 3.11+ (Python 3.14.8 was used for the current local run).
  • Java 17.
  • Apache Maven 3.9+ (the current workspace has Maven 3.10.0 under .tools).
  • Node.js 20.19+ and npm (Node 24.21.0 was used for the current frontend build).

Start the three services on Windows

Open three PowerShell terminals from the project folder.

# Terminal 1 — detector
cd .\detection-service
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
# Terminal 2 — Java API
cd .\backend
$env:DETECTION_SERVICE_URL = 'http://127.0.0.1:8000'
$env:FRONTEND_ORIGIN = 'http://localhost:5173'
mvn "-Dmaven.repo.local=$env:TEMP\redflagradar-m2\repository" spring-boot:run
# Terminal 3 — browser UI
cd .\frontend
npm install
npm run dev -- --host localhost

Open http://localhost:5173. For the current workspace, use the `.venv` interpreter explicitly if Windows’ python alias is unavailable, and invoke `.tools\apache-maven-3.10.0\bin\mvn.cmd` if Maven is not on PATH. Full steps are in the project README.

08 · Honest scope and roadmap

Limitations and future work

What the current prototype cannot establish

  • Whether the sender controls a real address, phone number, account, or domain.
  • Whether a company, scholarship, job opening, or payment policy is real or current.
  • Whether a URL has malicious reputation or is safe to open.
  • Whether a message is fraudulent merely because one phrase matches a rule.
  • That a low score or completed checklist means the user is safe.

Known technical constraints

  • Phrase rules are narrow and primarily English-language; paraphrases, slang, and other languages may be missed.
  • Legitimate messages can contain payment or deadline language, creating false positives.
  • The score weights are hand-authored and not calibrated against a representative, independently labeled dataset.
  • There is no authentication, rate limiting, deployment hardening, audit pipeline, or production observability in the local prototype.
  • The Next Move Coach uses evidence codes and fixed templates; it is not a conversational AI assistant.

Recommended roadmap

  1. Evaluate responsibly: create a consented, privacy-safe benchmark; report precision/recall and false-positive examples by scenario and language.
  2. Broaden language coverage: add reviewed multilingual and paraphrase rules, with language-aware UI and tests.
  3. Improve evidence mapping: connect each signal to an independent source type and explain what claim to verify there.
  4. Automate browser checks: include the coach’s text variants, clipboard success/failure, accessibility, responsive layout, and service errors in CI.
  5. Harden before deployment: define allowed origins, request limits, abuse protection, timeouts, logging policy, secret management, and retention rules.
  6. Keep claims honest: if external reputation data or machine learning is introduced, disclose sources, coverage, freshness, and failure modes.
